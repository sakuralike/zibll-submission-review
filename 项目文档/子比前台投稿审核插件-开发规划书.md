# 子比前台投稿审核插件开发规划书

## 文档目的

本规划书用于把《子比前台投稿审核插件-PRD》转化为可执行的开发、验证和发布计划。它保留 PRD 已经确定的产品边界，不替代 PRD；对尚未闭合的技术决策给出进入开发前必须完成的决策门和建议默认方案。

## 结论摘要

当前项目处于规划阶段。现有 PRD 已覆盖产品目标、范围、主题集成点、数据结构、安全要求、边界场景和验收用例，具备较好的需求基线；但当前工作目录中尚无插件实现代码，因此不能把文档完成度当作功能完成度。

建议采用以下交付策略：

1. 先冻结主题 API、页面模板加载方式、权限初始化方式和审核状态机，再开始业务编码。
2. 先交付模块 A 的最小闭环（我的投稿、前台审核、状态与权限），模块 B 小工具控制在核心审核链路稳定后以独立功能开关交付。
3. 所有审核动作必须以服务端状态机为唯一事实来源；前端按钮、页面隐藏和 AJAX 参数都只能作为体验层，不能承担安全职责。
4. 以 Zibll V9.0 作为开发基线，但在发布前用可执行的兼容性矩阵重新确认 V8.1、PHP 7.0 和 WordPress 5.0 是否仍然承诺支持。
5. 未通过决策门、集成测试和回滚演练前，不进入生产安装。

## 2. 产品范围与优先级

### 2.1 首期必须交付

首期以模块 A 为主，形成以下闭环：

- 插件依赖检测、激活保护、停用和卸载清理。
- 自动创建或复用独立投稿与审核页面。
- 用户查看自己的稿件、状态和审核意见。
- 具备权限的审核人查看待审队列和稿件详情。
- 服务端执行通过、驳回、退回三类动作。
- 审核历史追加保存，作者收到配置中的通知。
- 主题样式、权限矩阵、AJAX 返回协议和编辑器能力保持兼容。

### 2.2 第二阶段交付

模块 B 作为独立功能开关交付：

- 枚举已注册与已启用小工具。
- 按 `id_base` 配置登录可见性。
- 访客占位、隐藏、升级引导三种行为。
- CSF 轨过滤器和旧轨 callback 替换的双路径兼容。
- 管理员旁路、排除名单、多实例一致性和性能验证。

在模块 B 的双轨小工具夹具通过前，不应把它作为模块 A 的发布阻塞之外的“顺手功能”合并进核心审核代码。

### 2.3 明确不扩展的范围

继续遵守 PRD 的 N1-N10：不重写主题编辑器和上传、不做定时审核、不做 AI 审核、不做多级审核、不做实例级小工具权限、不改主题源码、不引入独立前端框架、不做前台批量审核、不做协作文编辑。

## 3. 开发前决策门

以下决策门必须在第一轮编码前关闭。每个决策门都要留下测试或源码证据，不能只在会议中口头确认。

| 编号 | 必须解决的问题 | PRD 中的依据 | 建议默认方案 | 通过证据 |
| --- | --- | --- | --- | --- |
| DG-01 | 插件模板如何被 WordPress 找到 | §6.1 声明主题未使用 `template_include`，示例却把插件模板当作页面模板并调用 `get_template_part('zsr/...')` | 先在基线站点验证插件自己的模板加载器。优先使用插件注册的 `template_include`/页面模板过滤器或明确的 `load_template()` 路径；插件模板不得依赖主题目录中的 `get_template_part()` 自动搜索 | 自动建页、直达 URL、404、主题升级各有一条浏览器用例 |
| DG-02 | 能力键何时初始化 | §4.3 示例只挂 `admin_init`，但前台请求也会先调用 `zib_current_user_can()` | 激活时幂等初始化，运行时在主题 API 可用后再做一次轻量 `ensure_capabilities()`；绝不覆盖已有 `zsr_*` 配置 | 首次前台请求、首次后台请求、主题设置重置、重复激活四组测试 |
| DG-03 | 审核状态机的唯一合同 | §6.5、`zsr_approve_keep_audit`、驳回后仍为 `pending` 存在组合歧义 | 先固定“状态对 + 允许动作 + 目标状态 + meta 变化 + 通知”的矩阵，再由一个纯 PHP 状态机函数执行；前端只消费矩阵 | 合法/非法迁移表全部通过，重复提交结果幂等 |
| DG-04 | nonce 函数的真实名称和参数 | 流程中写 `zib_ajax_verify_nonce()`，代码片段又出现 `zib_ajax_wp_verify_nonce()` | 以 V9.0 源码真实函数为准，封装插件自己的 `zsr_verify_nonce()` 适配层，避免业务代码散落主题函数名 | 静态扫描只允许适配层直接调用主题 nonce API |
| DG-05 | “审核记录”的可见范围 | §6.1 称“本机审核历史”，数据表只存最近 `zsr_reviewed_by`，历史则为序列化数组 | 明确为“当前审核人处理过的记录”还是“稿件完整历史”。建议页面显示完整历史，列表筛选通过历史数组或独立索引策略实现，不把单个最近审核人字段当作完整历史 | 两名审核人依次处理同一稿件，双方查看结果符合定义 |
| DG-06 | 小工具拦截的稳定入口 | §8.5 同时依赖 `widget_is_show_{id_base}` 和 callback 替换 | 先做 CSF、旧轨、同名 `id_base`、多实例四类夹具；CSF 过滤器优先，callback 只作旧轨兜底 | 锁定/解锁、登录/访客、管理员旁路和插件关闭均有 HTML 证据 |
| DG-07 | 小工具配置的唯一事实源 | §5.2、§7.3 规定 CSF 字段和独立 option 双写 | `zsr_widget_locked` 独立 option 作为唯一运行时事实源；CSF 只负责后台回显。保存、迁移、修复和冲突提示必须集中在一个同步服务 | 重置主题设置后配置仍在；双写不一致时可修复且有日志 |
| DG-08 | 兼容性承诺是否可兑现 | §8.1 同时承诺 PHP 7.0/WP 5.0、PHP 8.5/WP 6.8、Zibll V8.1-V9.0 | 先建立可运行的最低版本环境；若无法纳入 CI，则把未验证组合降为“目标兼容”而不是发布承诺 | 每个承诺组合有安装、激活、投稿、审核和卸载证据 |
| DG-09 | 页面所有权与重建规则 | §5.2、§7.6 允许自动建页，且卸载只移入回收站 | 用专属 post meta 标记“由插件创建”，记录 page ID、slug 冲突和管理员手工页面；只对带标记的页面执行重建/回收站动作 | 删除、改名、slug 冲突、重复激活和卸载均不制造重复页 |
| DG-10 | 通知失败的业务语义 | §6.4 要求站内信+邮件，但没有定义单通道失败时审核是否回滚 | 审核状态变更与通知发送解耦：状态成功即返回成功，通知失败记录可观测错误并按通道提示，不回滚已完成的审核；禁止通过修改全局 `$_REQUEST` 隐式传参 | 邮件失败、站内信不可用、作者注销和自审场景均可追溯 |
| DG-11 | 性能指标的可测定义 | §1.4、§10.3 中存在“0ms”“≤0.01ms”等过严或难以复现的指标 | 固定基线、请求样本、服务器规格、缓存状态和统计方法；以增量百分位和查询数作为门槛，不把单次测量当结论 | 同一环境重复测量并保存原始数据 |
| DG-12 | 文档中的规范冲突 | §9.4 禁止硬编码颜色，但示例仍写入多处颜色值；AC-01 写“全站短代码数量为 0” | 将约束改为“插件不注册 shortcode”；样式示例统一改成主题变量或标注为示意，不把示例误当验收规则 | 静态扫描规则与验收文字一致 |

### 3.1 进入编码的最低条件

只有以下条件同时满足，才进入业务模块编码：

- DG-01 至 DG-05 已有书面决策和最小测试。
- 目标 Zibll V9.0 源码快照、版本号和校验值已记录。
- WordPress、PHP、主题和数据库的开发环境可重复启动。
- 测试账号至少包含普通投稿人、版主、分区版主、超级版主、管理员和未登录访客。
- 插件主入口、依赖检测、错误日志策略和卸载策略已确定。

### 4.2 加载顺序

1. 主入口定义版本和常量，禁止直接访问。
2. 读取最小配置并执行主题/WordPress 版本检测。
3. 加载依赖适配层和纯函数域服务。
4. 在主题 API 可用后执行幂等能力键初始化。
5. 仅在后台加载设置页和小工具枚举；前台加载页面路由、权限和小工具运行时钩子。
6. 仅在插件页面加载 CSS/JS；小工具锁定只读取一次独立 option，不做枚举。
7. 缺失关键依赖时进入兼容模式，前台不白屏，后台显示缺失清单。

### 4.3 不修改主题的集成原则

- 不写主题文件、不改 `func.php`、不触碰 `inc/code/*.php`。
- 主题函数只通过适配层调用，业务代码不直接依赖易变的内部类。
- 不覆盖主题已有 `user_cap` 键；卸载只删除插件自己的键。
- 不替换主题原生投稿判定和通知，只追加插件入口或消费已有状态。
- 所有前台权限和状态校验在服务端重复执行。

## 5. 数据与状态合同

### 5.1 存储职责

| 数据 | 存储 | 规则 |
| --- | --- | --- |
| 插件设置 | `zsr_options` | CSF 管理，所有字段带 `zsr_` 前缀 |
| 小工具锁定 | `zsr_widget_locked` | 独立 option，运行时唯一事实源 |
| 能力键 | `zibll_options['user_cap']['zsr_*']` | 合并写入，不覆盖既有键，卸载只删除自己的键 |
| 稿件状态 | `post_status` + `zsr_state` | 两者必须由状态机成对更新 |
| 审核历史 | `zsr_review_history` | 只追加，单稿最多 50 条，保留快照 |
| 并发锁 | `zsr_lock_{post_id}` transient | 最长 60 秒，成功/失败都释放 |
| 页面所有权 | 页面 post meta | 记录插件创建的页面和当前插件版本 |

### 5.2 首期状态迁移合同

| 当前组合 | 动作 | 成功后的组合 | 作者可编辑 | 进入队列 |
| --- | --- | --- | --- | --- |
| `draft/draft` | submit | `pending/pending` | 是 | 是 |
| `pending/pending` | approve | `publish/approved`（默认） | 否 | 否 |
| `pending/pending` | reject | `pending/rejected`（默认） | 是 | 是 |
| `pending/pending` | return | `draft/returned`（默认） | 是 | 否 |
| `pending/rejected` | resubmit | `pending/pending` | 是 | 是 |
| `pending/returned` | resubmit | `pending/pending` | 是 | 是 |
| `publish/approved` | 任意审核动作 | 拒绝 | 否 | 否 |
| `trash/*` | 任意审核动作 | 拒绝 | 否 | 否 |

配置允许改变目标状态时，只能改变表中目标组合，不能绕过前置状态、对象类型、作者权限或动作白名单。`zsr_approve_keep_audit` 必须在实现前明确是“保持 `pending` 的批准标记”还是“二次审核队列”；在决策完成前不编码该分支。

### 5.3 审核动作的原子性与幂等性

每次审核按以下顺序执行：

1. 验证 nonce、参数类型和动作白名单。
2. 验证当前用户能力、稿件类型、当前状态和自审规则。
3. 获取稿件级短锁，并重新读取最新稿件。
4. 调用状态机计算唯一目标组合。
5. 追加历史记录并写入状态元数据；若关键写入失败，记录诊断并避免返回成功。
6. 更新 `post_status`，清理锁，最后触发异步意义上的通知适配。
7. 返回主题约定的 `error`、`msg`、`reload` 等字段。

重复请求必须返回“已处理或状态已变化”的明确结果，不能把第二次请求当成新的成功审核。

## 6. 分阶段交付计划

### 阶段 0：证据冻结与工程基线

**目标**：把 PRD 的源码事实变成可重复的开发基线。

**工作项**：

- 固定 Zibll V9.0 主题快照、WordPress/PHP 版本和数据库版本。
- 逐项复核 PRD 的函数名、钩子、行号和 CSS class，特别是 DG-01 至 DG-04。
- 建立本地 WordPress 测试站、可重置数据库和测试账号。
- 建立插件目录、代码规范、日志位置和最小 CI 命令。
- 建立 AC/EC/AQ 追踪表，规定每条用例的截图、HTTP、数据库或日志证据格式。

**退出条件**：依赖清单无未解释的致命项；模板加载与 nonce 函数已有可运行探针；任何未复核的 PRD 事实都被标注为待验证。

### 阶段 1：插件骨架与生命周期

**目标**：插件可安全安装、激活、停用、卸载，不提供业务入口。

**工作项**：

- 主入口、版本常量、文本域加载和依赖检测。
- 激活时初始化版本、数据库版本、默认设置和能力键。
- 兼容模式提示和后台诊断页。
- `uninstall.php` 的独立 option、能力键、transient 和插件创建页面处理。
- 最小翻译模板和构建检查。

**测试**：未安装主题、缺关键函数、重复激活、停用再启用、卸载、直接删除目录。

**退出条件**：所有失败路径不白屏；主题 option 中只出现插件自己的能力键；未创建业务页面或小工具副作用。

### 阶段 2：设置与权限

**目标**：后台能够配置能力、动作、通知和功能开关，且前后台判定一致。

**工作项**：

- 独立 CSF 设置页和字段校验。
- `ensure_capabilities()` 与社区身份过滤器适配。
- 默认权限、超级管理员兜底、仅本人/可审核他人规则。
- 动作至少保留一项、原因长度、状态目标和通知通道的服务端校验。
- 小工具设置先只保存，不在此阶段启用拦截。

**测试**：普通用户、认证用户、VIP、版主、分区版主、超级版主、管理员和无权限用户的矩阵测试；主题设置重置后的能力恢复。

**退出条件**：无权限用户无法通过直链或伪造请求进入审核接口；配置保存不会覆盖已有主题权限。

### 阶段 3：页面路由与我的投稿

**目标**：完成作者侧可见的页面和稿件生命周期。

**工作项**：

- 页面所有权、自动建页/复用、slug 冲突和模板加载器。
- `submit`、`my`、`detail`、`edit` 视图白名单。
- 复用主题编辑器、分类、标签、媒体上传和页面骨架。
- 我的投稿查询只返回当前作者允许的状态。
- 投稿、草稿、编辑、重新提交和状态徽章。
- 页面资源按需加载、禁止索引和登录引导。

**测试**：未登录访问、无投稿权限、本人/他人直链、空标题、分类删除、主题关闭文章功能、主题暗色模式。

**退出条件**：AC-01 至 AC-07 通过，且页面模板加载不依赖主题目录中的同名插件模板。

### 阶段 4：审核台与状态机

**目标**：完成前台审核核心闭环。

**工作项**：

- 待审核查询、分页、详情预览和审核操作区。
- 状态机纯函数及非法迁移拒绝。
- `zsr_review` AJAX、nonce 适配、参数清洗和权限顺序。
- 稿件级短锁、状态重读和重复提交处理。
- 审核历史追加、作者/审核人可见范围和状态徽章。

**测试**：通过、驳回、退回、重复审核、自审、他人稿件、并发、伪造动作、非 `post` 类型、非 `pending` 状态、超长/HTML 意见。

**退出条件**：AC-08 至 AC-15、AC-17、AC-18 和 EC-05 至 EC-12 通过；数据库状态、历史和响应协议均有证据。

### 阶段 5：通知与可观测性

**目标**：把审核结果可靠地告知作者，并能定位通道失败。

**工作项**：

- 站内信和邮件通道适配器，不在业务代码中直接依赖主题内部细节。
- 处理主题通知函数的参数前提、作者自审和作者注销。
- 记录通道成功/失败、稿件 ID、动作和相关错误码；不记录正文、nonce 或敏感凭据。
- 明确通知失败不回滚审核状态的界面提示。

**测试**：双通道、单通道、全关闭、邮件失败、站内信缺失、自审和用户删除。

**退出条件**：AC-10、AC-11、AC-16 通过；失败通道不会制造重复审核或静默丢失。

### 阶段 6：小工具登录可见控制

**目标**：在不影响审核链路的前提下交付模块 B。

**工作项**：

- 已注册/已启用枚举、侧边栏和实例数量展示。
- 独立 option 同步和冲突修复。
- CSF `widget_is_show_*` 过滤器路径。
- 旧轨 callback 替换路径，保持 `before_widget` 结构。
- 访客三态、管理员旁路、排除名单、多实例一致性。
- 默认关闭、插件缺失时自动失效和诊断日志。

**测试**：CSF 轨、旧轨、商城/社区小工具、同名 id_base、未启用小工具、主题注销小工具、登录/访客/管理员、页面多侧边栏。

**退出条件**：AC-19 至 AC-30 通过；默认关闭时非小工具页面没有可测的额外查询或资源。

### 阶段 7：兼容性、安全与性能门

**目标**：将功能验收转为发布证据。

**工作项**：

- 兼容性矩阵安装/激活/核心流程回归。
- PHP 静态检查、WordPress 安全扫描、未转义输出和 nonce 检查。
- 主题升级/降级模拟、主题设置重置、缓存和大量待审稿件测试。
- CSS/JS 大小、前台请求、查询数、TTFB 和错误日志基线比较。
- 生成翻译模板、打包清单和升级迁移报告。

**退出条件**：AQ-01 至 AQ-12 全部有证据；未达标项目有明确阻塞标记，不以“人工确认”代替。

### 阶段 8：Staging、发布与回滚

**目标**：在真实拓扑中安全启用。

**发布顺序**：

1. 备份数据库和插件目录，记录主题版本、PHP/WP 版本及当前 `zibll_options` 摘要。
2. 在 Staging 安装插件并执行迁移、全量冒烟和浏览器验收。
3. 先启用模块 A，观察错误日志、审核失败率和通知通道。
4. 确认模块 A 稳定后再打开小工具功能开关。
5. 生产小范围启用，保留关闭 `zsr_enable` 和 `zsr_widget_enable` 的快速回退路径。

**回滚**：优先停用插件并关闭功能开关；若代码回滚，保留稿件 `post` 和 `zsr_*` meta，按迁移版本执行向后兼容处理；不要直接删除主题文件或批量删除稿件数据。

## 7. 测试与证据计划

### 7.1 测试层级

| 层级 | 重点 | 最低证据 |
| --- | --- | --- |

| 安全测试 | 越权、CSRF、XSS、路径/参数注入、重复请求 | 请求与响应对照 |

| 升级卸载测试 | 版本迁移、停用、卸载、目录删除 | option/meta/page 前后快照 |

### 7.2 测试账号与夹具

至少准备以下账号和数据：

- 普通已登录用户、认证用户、VIP、版主、分区版主、超级版主、管理员、未登录访客。
- 草稿、待审、已驳回、已退回、已通过、回收站各一篇。
- 两名审核人同时打开同一待审稿件。

### 7.3 验收追踪规则

## 8. 风险登记表

| 风险 | 影响 | 概率 | 缓解措施 | 触发后的处理 |
| --- | --- | --- | --- | --- |
| 页面模板未被 WordPress 解析 | 全部前台功能不可用 | 高 | DG-01 探针、插件模板适配层、自动建页测试 | 停止阶段 3，回到装载方案决策 |
| 能力键只在后台初始化 | 前台用户全部被误拒或出现权限漂移 | 高 | 激活 + 运行时幂等初始化 | 禁止上线，保留原主题权限 |
| 状态和 meta 写入不一致 | 审核结果错误、无法追溯 | 高 | 状态机、短锁、重读、失败证据和补偿策略 | 暂停审核入口，保留稿件并人工核对 |
| 主题通知函数静默失败 | 作者收不到审核结果 | 中高 | 通知适配器、通道日志和独立失败提示 | 切换邮件或关闭通知，不回滚内容状态 |
| 小工具 callback 替换破坏 HTML | 全站布局或功能异常 | 高 | 默认关闭、双轨夹具、HTML 快照和快速开关 | 关闭模块 B，保留模块 A |
| 主题升级改变内部钩子 | 功能失效或 PHP 错误 | 中高 | 依赖自检、兼容模式、版本矩阵和升级回归 | 阻断激活并显示缺失清单 |
| `zsr_options` 与独立 option 漂移 | 后台显示与前台行为不一致 | 中 | 单一事实源、同步修复和冲突提示 | 以独立 option 为准并记录修复 |
| 深分页/历史 meta 变慢 | 审核台超时 | 中 | 页数上限、查询限制、缓存待审计数、性能基线 | 引导后台处理并保留诊断指标 |
| 文档事实过期 | 错误调用主题 API | 中 | 每次主题版本变更重跑事实核对 | 标记兼容模式，不宣称支持 |

## 9. 发布门槛

满足以下条件才允许发布：

- PRD 中的未决技术项已经在决策表中关闭，且实现与决策一致。
- 模块 A 的 AC-01 至 AC-18、关键 EC 和通用 AQ 有可复核证据。
- 模块 B 若随包发布，AC-19 至 AC-30 全部通过；否则保持功能关闭并明确未交付。
- 主题目录 `E:\只比主题\zibll` 无变更，插件无独立前端框架和外部 CDN。
- PHP/WordPress/Zibll 兼容性承诺与实际测试矩阵一致。
- 错误日志无插件产生的 notice、warning、deprecated 或 fatal。
- 卸载和回滚不删除稿件正文、审核历史或非插件设置。
- Staging 冒烟、浏览器验收、通知通道和回滚演练均完成。

## 10. 待确认事项

以下问题需要产品或维护者在开发前明确；规划书给出的默认建议仅用于推进，不视为已批准变更：

1. 首期是否只发布模块 A，模块 B 是否延后到第二个交付批次。
2. 驳回默认保留 `pending/rejected`，还是直接回到 `draft/returned`。
3. `approve_to_status=pending` 与 `zsr_approve_keep_audit` 的区别和使用场景。
4. 审核记录页面显示当前审核人历史，还是显示稿件完整审核历史。
5. 审核通知失败是否只告警，还是需要后台重试队列。
6. 是否真正承诺 PHP 7.0、WordPress 5.0、Zibll V8.1；若没有可运行环境，应如何缩小支持范围。
7. 页面模板采用插件过滤器加载还是虚拟页面兜底作为主路径。
8. 小工具批量操作是否属于首期验收，还是仅保留逐项开关。
9. 站点已有同名 `submissions` 页面时，管理员选择复用、改 slug 还是停止自动建页。
10. 审核历史最多 50 条是否满足长期站点需要，是否需要未来迁移到独立表。

## 11. 下一轮实际执行顺序

在开始写业务代码时，按以下顺序执行，每一步完成后保留证据：

1. 固定并核对 Zibll V9.0 源码快照和环境矩阵。
2. 完成 DG-01 至 DG-05 的探针和决策记录。
3. 建立插件骨架、依赖检测、激活/停用/卸载测试。
4. 实现选项默认值、版本迁移和能力键幂等初始化。
5. 实现页面所有权、模板加载器和“我的投稿”只读查询。
6. 实现投稿/编辑 AJAX 和状态机单元测试。
7. 实现审核台、并发锁、历史和通知适配器。
8. 完成模块 A 的浏览器与安全验收。
9. 在独立开关下实现并验证小工具控制。
10. 执行兼容性、性能、升级、卸载、Staging 和回滚门禁。
